# Plan — Android 14 (LineageOS 21) on a PX6 / HCT4 unit with the shipped vendor + kernel

Decisions locked (see `docs/decisions.md`): target **Android 14**, base **LineageOS 21**,
kernel = **shipped 4.19 binary first, rebuild from BSP source later**, vendor = **blobs untouched +
wrappers**, apps = **keep HCT4 apps for v1**, security = **pragmatic during bring-up, strict at
release**, delivery = **Update.zip on USB stick** through the unit's existing upgrade flow - and that
delivery decision is now superseded by **D25** (the stock recovery only trusts HCT's own cert, so the
first install runs raw `super.img`/`boot.img` via `adb root` dd from Android 11, `docs/flash.md`).

## Architecture of the ROM

We do **not** rebuild `vendor`. The build produces new `system` / `product` / `odm` (+ APEXes) and a
new `boot.img` (old 4.19 kernel binary + Lineage 21 first-stage ramdisk + second stage). The shipped
`vendor.img`, `uboot.img`, `trust.img`, `dtbo.img`, `RKLoader.bin` and `/data` are left untouched.
Everything Android 14 needs that the old vendor lacks is added **in our own partitions**:

| Needs Android 14 | Where it goes |
|---|---|
| KeyMint (`IKeyMintDevice`) | built from AOSP source, installed into our vendor-overlay partition or as a system-side service; declared in the device manifest we ship |
| `libhardware_legacy`, hwc2-on1/onfb adapters, `libchrome`, `libion` | vendor-local copies built from Android-10 sources, installed in `/vendor` (a small "shim overlay" written into the existing vendor image, or as an appended `vendor` logical partition we rebuild with the same blobs) |
| device manifest / compatibility matrix | Android 14 versions generated by our device tree |
| SELinux policy | rebuilt from Lineage 21 + our vendor sepolicy additions (Android 10 vendor labels mapped forward) |
| fstab | Android 14 variant pointing at the same block names, keeping F2FS `/data` |
| super layout | `dynamic_partitions_op_list` for the **unchanged** group (3,258,974,208 B, **D19** - no resize, no GPT write); Android 14's five logical partitions incl. `system_ext`, and `vendor_ramdisk` if Android 14 needs it |

## Pre-flight (mandatory before any flashing)

The unit currently runs **Daisaita/Daitsun firmware**, not this reference Hal9k/HCT4 firmware, and is
**not rooted**. Consequences:

1. Vendor equivalence: the live unit's HAL set now matches the reference manifest (only `cas`,
   `weaver`, `rockit.hw` are undeclared, their binaries still present), and `/dev/mtc-*` nodes exist.
   The next probe hashes every vendor blob so `tools/blob_diff.py` can prove byte-for-byte equality
   with `analysis/vendor_tree/` - that is the gate before any flash.
2. **Backup before touching anything**: the reference `update.zip` is on disk already; the zip
   currently installed (Daisaita/Daitsun) must be obtained or reproduced by `dd`-ing the partitions
   (see M2b step 1). With a single unit there is no hardware fallback, so a failed flash must always
   be recoverable.
3. Data collection: originally `allinone.sh` (probe + LAN upload, kept outside the repo), now
   `scripts/probe.sh` for Android 10/11 and the in-ROM `/system/bin/hu_probe.sh` for Android 14
   (`docs/findings.md`, "No terminal on the unit"). No adb and no root needed on the running firmware;
   `/system/xbin/su` is blocked there, so root comes from `adb root`.

### M1b — getting the report back to the PC (no SD-card shuffling)
Workstation runs `scripts/upload_server.py` (LAN HTTP endpoint, writes into `incoming/`, gitignored).
Phone/unit side: `scripts/upload_client.sh` (needs `pkg install curl` in Termux).
Firewall: ufw is enabled, so a **runtime-only** rule is open while the server runs
(`sudo ufw allow 8765/tcp`); close it afterwards with `sudo ufw delete allow 8765/tcp`.
The shared token lives outside the repo (`/tmp/opencode/upload_token.txt`) - never commit credentials.
For partition backups restart the server with a bigger cap: `UPLOAD_MAX_BYTES=$((4*1024*1024*1024))`.
Fallback if the endpoint is not running: `scp probe.md Daan@192.168.1.161:.../incoming/`
(password prompted interactively, not stored anywhere).

### M2 — environment + device tree skeleton
- Workstation: ~120 GB free for the Lineage 21 tree + ~30 GB for build output (we have 518 GB free).
- `repo init` LineageOS 21 (`lineage-21.0`), `repo sync` (hours; ask before starting).
- `device/rockchip/rk3399-px6-hct4/`:
  - `BoardConfig.mk`: dynamic partitions, no AVB (`BOARD_AVB_ENABLE := false`), boot header v2

  - `device.mk`: inherit nothing from Rockchip vendor source; import prebuilt vendor tree

  - `manifest.xml`: Android 14 format, `target-level="4"` (vendor stays Android 10) + KeyMint entry +

### M2b - partition layout: no change (**D8 superseded by D19, Nov 6**)
Super (p14) stays 3,263,168,512 B and the group stays 3,258,974,208 B. Android 14's logical images
total 2,183,183,264 B block-aligned (system 929 MB, vendor 412 MB, product 456 MB, system_ext 385 MB,
odm 0.8 MB) - *smaller* than the stock Android 10 layout's 3,125,321,728 B - so the existing partition
already carries them with ~1.07 GiB spare. The payload's `dynamic_partitions_op_list` recreates the
logical partitions inside super; no partition table byte is written (**D18**), and `sgdisk` is not
installed for this work.

What this milestone does instead:
1. Keep the `analysis/gpt/` head/tail bytes as a record (read-only, from `gdisk -p`).
2. `/data` is reformatted on install, so the unit boots into its first-run setup (HCTProvision).
   **Owner confirmed losing accounts/apps/settings is fine** (D10), so no personal-data backup.
   Cheap context only: `pm list packages -f` (the app set, to reinstall the same list) and photos of
   the current HCT settings if the owner wants them reproduced - the non-trivial ones are the
   steering-wheel key mapping (HCTWheelStudy), radio/DAB station list and DSP/EQ presets.
3. Verify the partition sizes after install with the SD-card probe (sysfs sizes, no root) against
   `misc_info.txt` before judging anything else.
4. `BOARD_SUPER_PARTITION_SIZE` stays 3,263,168,512 (`analysis/hu_partition_offsets.txt`); if the
   images ever outgrow the group that is a fresh decision (**D19**), not a scripted GPT rewrite.
5. Then run M3's install.

Delivery of the install package (D10): the zip goes on the SD/USB stick and an updater app hands it
to recovery via `RecoverySystem.installPackage()`; AOSP/LOS recovery has no SD-card menu, so this is
the SD-card route that actually works. ADB sideload from the NAS is the fallback.

The very first install is not an OTA of our own recovery: it runs in the **stock** recovery with the
**stock** `update-binary` and writes the logical partitions inside super plus `boot` (**D18**).
`recovery`, `uboot`, `trust`, `dtbo`, `RKLoader.bin` and `security` are never written, so the stock
recovery keeps its loader path to the mainboard MCU firmware.

Rollback is the official Android 10 `update.zip`, flashed the same way (owner decision Nov 6 - no
restore tooling in this repo). The unit factory-resets either way and the owner re-adds accounts/apps.

Re-setup checklist after a factory reset (owner's part, cheap): accounts, launcher, BT phone pairing,
CarPlay/AA pairing, WiFi password, GPS map download, radio/DAB station scan, steering-wheel key
learning (`HCTWheelStudy`), AV-in camera calibration, DSP/EQ presets, clock + region. The HCT apps
ship defaults, so the unit is usable immediately after setup; only the calibration items above need
doing by hand, and that is why the optional `/data/data` tar (step 2) is worth taking when `su` works.
### M3 — boot test (framework-only flash)
The image we flash first is deliberately **plain LineageOS + the prebuilt vendor image**: it carries
our fstab/ueventd/init overlays and the framework feature XMLs, but **no HCT apps** (they live in the
stock `system` partition, which our build replaces wholesale). Purpose is boot + HAL plumbing, not
feature parity.
1. Backup done in M2b (partition dump + userdata content + current zip). Re-verify it reads back before flashing.
2. Build a test zip that only replaces `system`, `product`, `odm` (+ our shims) and `boot.img`.
3. Boot acceptance: `sys.boot_completed=1`, SurfaceFlinger up, `audioserver` up, `keystore2` up, and
   the hardware reachable from the framework (tuner/AMP nodes, CAN/MTC, GPS, BT, AV-in paths).
   App-level feature parity is checked in M10, once the HCT apps are in the image.
   Failure modes to watch: vendor ramdisk missing, libion absent, hwc2 adapter absent, VINTF mismatch.

### M9 - WiFi 5 GHz for wireless CarPlay / Android Auto
Wireless CarPlay/AA need a 5 GHz AP. The unit's WiFi is **not** an internal module: `wlan0` and
`p2p0` sit under `/sys/devices/platform/fe3c0000.usb/.../net/`, i.e. a USB adapter with
`modalias usb:v0BDAp0179` = Realtek **RTL8188E family**, which is 2.4 GHz silicon. No firmware
change can create 5 GHz on that chip.
- **Hardware fix (recommended)**: swap the USB WiFi module for a dual-band Realtek RTL8821CU or
  RTL8822BU. The shipped vendor already carries `8821cu.ko` and `8822bu.ko` in
  `/vendor/lib/modules`, so no kernel rebuild is needed - only module loading in
  `init.connectivity.rc` and a correct regulatory country code (`iw reg set`, kernel regdb is
  mandatory on this build: `CONFIG_CFG80211_REQUIRE_SIGNED_REGDB=y`).
- **HAL/framework level** (**D21**, Nov 7): Android 14 has no HIDL wifi support, so the stock
  `wifi@1.0-service` blob cannot serve it. The control plane is rebuilt in our tree: `libwifi-hal-rtk`
  from published Apache-2.0 source + `BOARD_WLAN_DEVICE := realtek` + the AIDL
  `android.hardware.wifi-service`/supplicant/hostapd services, which declare the wifi entry in the
  vendor manifest. The driver itself needs no rebuild (`8188eu.ko` is nl80211-standard). Band reporting
  still has to come from the driver (`iw list`, `WifiCapabilities`) or Android hides the AP list.
- `CONFIG_MAC80211_RC_MINSTREL_VHT` is off in the shipped config: 5 GHz works but VHT rate control
  is not tuned, so throughput is lower; that is a kernel-config item if we rebuild.
Fallback if no hardware swap: wired CarPlay/AA only (works today). **D12: the owner declined the
dongle for now**, so wireless CarPlay/AA is out of scope; the swap stays documented as the one-line
fix if that changes.

### M10 - HCT app layer + optional GApps (capacity)
The stock app layer is 11 HCT apps (`system/app/HCT4BlueTooth`, `HCT4BtMusic`, `HCT4FileBrowser`,
`HCT4Movie`, `HCT4Music`, `HCT4Radio`, `HCT4UsbIpod`, `HCT8AmpSetup`, ...) plus `init.hct.rc`. Their
APKs are 67.9 MB and 113.4 MB counting the shipped `oat/` blobs (`analysis/system_files.txt`). Our
build does **not** include them yet - it replaces the whole `system` partition with LineageOS's own,
so the first image is a boot test, not a feature-parity build. Re-adding them is a `PRODUCT_COPY_FILES`
/ prebuilt-module step (D6), plus whatever privapp permissions and signature assumptions they need.

Space on the current table (D11 option A): the super group is 3,258,974,208 B and our five logical
images take 2,056,466,432 B, leaving **1,202,507,776 B (1,147 MiB)** spare. LineageOS 21's
MindTheGapps arm64 package is 431,524,182 B compressed and lands at roughly 550-650 MB across
`system`/`product`/`system_ext`. So HCT apps (~113 MB) + full GApps (~600 MB) = ~713 MB fits today with
~430 MB to spare, and a pico/nano-style subset leaves far more room. Inside the existing super (super
group 8,585,216,000 B) the question is moot.

Two caveats before baking GApps in:
- Sideloading MindTheGapps *after* our OTA asserts against the LineageOS build fingerprint it was
  built for; our unofficial build has its own fingerprint, so the reliable route is to put the GApps
  APKs into our own build, not to install the vendor's zip afterwards.
- Adding content changes each logical partition's size, so the OTA's `dynamic_partitions_op_list` must
  carry the new sizes (`m otapackage` regenerates it; `m superimage` restages super).
